## Hard constraints — DO NOT break existing behaviour

1. **Do not change any existing data.** No `UPDATE`/`DELETE` of existing rows, no backfills that overwrite values, no altering/dropping/renaming existing columns, tables, functions, triggers, RLS policies or views.
2. **Do not change any existing logic.** Do not edit calculation code in `ctcEngine.js`, `salaryMonthProcessing.js`, `salaryDb.js`, `salaryData.js`, `payrollRulesDb.js`, `src/modules/payroll/calc/*`, `src/modules/payroll/formula/*`, the month-run lock / reprocess RPCs, payslips, bank export, or the salary register. Reports are **read-only consumers**.
3. Changes are **additive only**: new migrations (new tables / new views / new RPCs / new nullable columns only where unavoidable), each with a matching rollback in `supabase/rollbacks/` following the existing naming pattern (`YYYYMMDDHHMMSS_name.sql` + `_down.sql`). Use `CREATE … IF NOT EXISTS`.
4. Hooking into the lock flow (for snapshot + row creation) must be done with a **new AFTER trigger or a new function called after the existing lock succeeds** — never by rewriting the existing lock RPC (`20261005220000_admin_salary_month_run_lock.sql`). If the lock fails, nothing new must run; if the new step fails, it must not roll back or block the existing lock unless the spec explicitly requires blocking (it doesn't for lock).
5. Reuse existing helpers/UI patterns (Excel export like `salaryProcessingExcel.js`, privacy masking in `salaryPrivacy.js`, access in `salaryAccess.js`, theme per `THEME.md` / `TYPOGRAPHY.md`). Match surrounding code style.
6. **First, investigate before building:** map every field the spec names (below) to the actual existing tables/columns (month run header & status, run lines, earning/deduction heads, OT, incentive, arrears, er_pf/er_esi/er_lwf, gratuity/bonus provisions, insurance, employee master fields, increment/revision history, etc.). Produce a mapping table and list every field that **does not exist yet**. For missing data, propose additive new tables/columns and ask me before creating them. Do not guess or fabricate fields.
7. Run lint/build/tests at the end; confirm the existing salary processing, lock, payslip and register outputs are unchanged.

## Common rules (apply to ALL 7 reports)

1. **Source:** read only from payroll runs with status = **LOCKED**. Never from draft or recalculating runs.
2. **Snapshot:** on lock, save each employee's **vertical, department, grade and location** as they were that month. Reports use this snapshot, so a transfer next month does not change last month's report. (New snapshot table, populated on lock; additive.)
3. **Standard filters on every report:** Period (month / range / quarter / FY Apr–Mar / YTD), Vertical, Department, Location, Cost centre, Grade, Employment type.
4. **Comparison columns:** wherever "Previous" appears, it means the **immediately previous locked month** for the same filters.
5. **Change % = (Current − Previous) ÷ Previous × 100**, rounded to 1 decimal. Show **"New"** if Previous = 0.
6. **Rounding:** store to 2 decimals; display whole rupees with Indian grouping (12,34,567).
7. **Report header** on every screen and download: company name, report name, period, filters applied, generated on (date and time), generated by (user).
8. **Downloads:** Excel (values, not formulas), PDF, CSV.
9. **Drill-down:** clicking any total opens the employee-level rows that make it up.
10. **Access:** per role (Directors see all; vertical heads see own vertical only). **Log every view and download** (new audit-log table: user, report, filters, period, action view/download+format, timestamp).

## Standard cost definitions

| Term | Formula |
|---|---|
| Gross | Sum of all earning heads for the month (incl. OT, incentive, arrears) |
| Employer statutory | er_pf + er_esi + er_lwf |
| Employer cost | Employer statutory + gratuity_prov + bonus_prov + insurance |
| Total CTC cost | Gross + Employer cost |
| Net pay | Gross − all employee deductions |
| Headcount paid | Count of employees with a line in the locked run and paid_days > 0 |

Implement these once (shared SQL view/RPC or one JS module) and use them in every report so figures tie across reports.

## Report 1 — Monthly Payroll Summary

- **Purpose:** one-page snapshot of the month's payroll for Directors. **Users:** MD, Directors, CFO. **Generated:** automatically on payroll lock. **Format:** dashboard tiles + PDF.

| Row (metric) | Calculation |
|---|---|
| Headcount paid | COUNT(emp_code) where paid_days > 0 |
| Gross earnings | SUM(gross) |

## Report 2 — Month-on-Month Variance

- **Purpose:** explain every rupee of change in Total CTC between two months. **Users:** MD, CFO. **Generated:** on lock. **Format:** table + waterfall chart, PDF and Excel.
- Compare the two locked runs **employee by employee**. All drivers except the last are measured on **gross**; employer cost is one separate line. The drivers must add up **exactly** to the total change.

| Driver | Which employees | Amount = |
|---|---|---|
| New joiners | In current run, date_of_joining in current month | Their current gross |
| Exits | date_of_exit in current or previous month | Current gross − previous gross (negative) |
| Increments / promotions | In both runs, with an entry in the increment log effective this month | Change in fixed pay heads |
| Overtime | In both runs | Current ot_amount − previous ot_amount |
| Incentives and arrears | In both runs | Change in incentive + arrear heads |
| Loss of pay / attendance | In both runs, no increment | Change in gross caused by change in paid_days |
| Other | In both runs | Remaining change in gross not explained above |
| Employer statutory and provisions | All | Current employer cost − previous employer cost |

**Check:** Previous CTC + all drivers = Current CTC. If not equal, **block publishing and show the difference**.

|---|---|

| Employer PF (incl. EPS, EDLI, admin charges) | SUM(er_pf) |

## Report 7 — Compliance Due-Date and Payment Tracker

- **Purpose:** confirm every statutory payment is made on time and show any interest or penalty paid. **Users:** CFO, compliance team. **Generated:** live (refreshes daily); rows created automatically on payroll lock. **Format:** dashboard with colour status, Excel.

**How rows are created:** On lock of wage month M, create **one row per statute** using Report 6 "Total to deposit". Due date comes from a **compliance calendar master** (statute, state, day of month, months applicable), e.g. TDS on the 7th and PF / ESI on the 15th of month M+1. Accounts staff enter paid_on, challan_ref, interest and penalty when they pay. (Rows go into a new statutory payments table; re-locking must not duplicate rows — upsert on wage_month + statute + state.)

**Status logic:**

| Condition | Status | Colour |
|---|---|---|
| paid_on is blank and today < due_date − 3 days | Pending | Grey |
| paid_on is blank and today within 3 days of due_date | Due soon | Amber |
| paid_on is blank and today > due_date | Overdue | Red |
| paid_on ≤ due_date | Paid on time | Green |
| paid_on > due_date | Paid late (show days late) | Red text |

Days late = paid_on − due_date. **Alert email to CFO and compliance team on Due soon and Overdue** (reuse the existing server email infrastructure, e.g. pattern in `server/salaryCtcEmailApi.js`; daily scheduled check).

| Sep 2026 | PF | 15 Oct 2026 | 8,20,000 | — | — | Pending | — | — |
